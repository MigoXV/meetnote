# 单场会议上下文复用与前缀缓存研究

研究日期：2026-10-26。基于 `7d6247a` 新建 `research/ucl-prefix-cache`，先完成纪要缺失修正，再开展本研究。

结论：借鉴 Zoom UCL 的上下文复用方向，但应继续建设现有的会议证据状态，重点补齐议题版本、局部失效及全局覆盖校验。当前模型的前缀缓存已生效；较长且稳定的前缀能明显降低首 token 延迟，无法直接减少长纪要的解码工作。本分支提供真实服务基准、布局实验和按任务缓存统计，没有引入数据库、第二个 LLM 或未经验证的议题生成流程。

## 官方资料与适用边界

Zoom 在 2026-10-20 发布的 UCL 连接会议、聊天等对话上下文与文档、业务数据，其 [Agentic Search 说明](https://www.zoom.com/en/ai-research/agentic-search-zooms-context-layer-for-every-ai-agent/)区分检索结果接口和在服务端检索、综合后返回答案的接口。它提供了上下文复用的产品方向，不能据此推断其内部采用了我们需要的会议事实状态机、议题覆盖算法或 KV 缓存方案。[Zoom 官方介绍](https://www.zoom.com/en/blog/unified-context-layer-for-it/)。

[QMSum 的 Locate-then-Summarize](https://aclanthology.org/2021.naacl-main.472/)研究的是按查询选择相关会议内容再总结；它不能替代完整纪要对全部重要决定和行动的覆盖检查。本项目应从事实账本枚举应覆盖事项，再用检索补充证据；不能将检索 top-k 当成整场会议的内容目录。这是面向本项目的设计判断。

[vLLM 0.18.0 APC 文档](https://docs.vllm.ai/en/v0.18.0/features/automatic_prefix_caching/)说明缓存重用相同 token 前缀，主要加速 prefill，不能直接加速 decode。当前运行的是 vLLM **0.18.0** 与对应 Ascend 实现，不应套用调研材料中 0.8.5／0.14.1 的默认值。本机已经开启 prefix caching，启用 MTP2 与异步解码图；无须为本实验再打开开关或扩大 KV 配额。

## 当前代码已经做了什么

| 能力 | 已有实现 | 仍需补齐 |
| --- | --- | --- |
| 原文边界 | `Source` 保存稳定 ID、字符位置、说话人和时间；入口复用 `MeetingEngine` | 18095 适配器目前主要提交文本和片段 ID；不能把未确认说话人直接用于责任归属 |
| 新增输入 | `extract()` 处理新增批次，最多带 512 token 邻近前文 | 不必重新抽取整场原文；短批次的 prefix cache 收益可能有限 |
| 会议状态 | `KnowledgeState` 保存事实、来源、修订及状态；单消费者提交 | `Fact.topic` 是可变显示文本，尚不是稳定议题主键 |
| 关系处理 | NPU BGE-M3 召回历史候选，模型核验证据，修订留历史 | 向量相似度不能直接确定撤销、覆盖或全局重要性 |
| 纪要 | 在预算足够时保留完整候选证据，最终独立审校一次 | 长会议超预算时仍需有界选择；尚无独立的全局议题覆盖保证 |
| 应用缓存 | `Context` 复用完全相同的任务输入；向量缓存按会议限额 | 一个新议题加入后，整篇成文请求仍会改变，需要更细的依赖失效范围 |

实现依据：[引擎](../src/meetnote/engine/runtime.py)、[状态类型](../src/meetnote/domain/state.py)、[任务缓存](../src/meetnote/engine/context.py)、[向量客户端](../src/meetnote/embeddings/client.py)。因此，现状不是“把三万字一次性交给模型”的单次总结架构，也不需要从零重建分段抽取。

## 真实缓存基准

复用现有 `qwen3.8-27b-optimized-v1` 实例：单卡 910B、W4A8 模型、BF16、MTP2、ACL Graph、四路容量、57344 输入／8192 输出容量、8192 batch tokens、22.5 GiB KV。实验不改启动参数，不新增 LLM 实例。BGE-M3 保持 NPU 部署。

测量串行执行，每档三轮。每轮使用全新随机前缀取得未命中基线，随后重复完整输入，再只修改末尾问题。均输出固定上限 **64 tokens**；长度终止 `incomplete` 是本性能实验的预期结果，不是交付纪要的成功标准。命中以响应 `usage.input_tokens_details.cached_tokens` 为准，而非仅根据请求相似性判断。

| 实际输入 token，约 | 未命中 TTFT | 重复输入 TTFT | TTFT 加速 | 未命中总耗时 | 重复输入总耗时 | 重复输入命中 token |
| --- | --- | --- | --- | --- | --- | --- |
| 1119 | 0.643 秒 | 0.635 秒 | 无实质缓存收益 | 1.620 秒 | 1.609 秒 | 0 |
| 8290 | 3.036 秒 | 0.991 秒 | 3.06 倍 | 4.030 秒 | 1.987 秒 | 6144，约 74% |
| 32865 | 12.232 秒 | 1.233 秒 | 9.92 倍 | 13.236 秒 | 2.275 秒 | 30720，约 93% |

表中均为三轮中位数。只改末尾问题时也得到相同的命中 token 数，8K／32K TTFT 分别约 0.994／1.233 秒。输出阶段约一秒，没有观察到系统性的 decode 提速；客户端首 delta 可能携带多个 MTP token，所以报告的首 delta 后输出速率只作近似指标。

这不是整份纪要的加速倍数。纪要可能生成数千 token，decode、抽取、关系核验与审校均计入总耗时，端到端收益会更小。只有三轮串行合成测试，未覆盖四路稳态、长会议质量、显存峰值或缓存受其他流量挤占的情形。部分自由生成输出的哈希在重复请求间不同，短输入未命中对照也存在这种变化，不能将本性能测试作为缓存前后逐 token 等价或业务质量证明。

LLM 进程在两组基准前后均为 PID 3477553，NPU 工具报告常驻使用量均为 48247 MB；这是采样值，不是峰值监测。权重、KV 配额和最大批次没有增加。缓存占用复用原有 KV 池，未额外预留缓存显存。

全部测试结束后，按原启动参数重启模型，释放测试预热保留的临时分配。恢复后模型就绪，LLM 进程占用为 46819 MB，低于任务开始时采样的 46943 MB；BGE-M3 仍运行在 NPU。该重启发生在上述基准完成之后，不影响同一实例内的配对数据。

原始数据：[缓存对照](prefix-cache-results.json)、[布局对照](prefix-layout-results.json)。文件只保存合成测试的数值、配置、随机标记及输出哈希，不保存会议内容或生成正文。

## 为什么当前成文请求难以命中

本机混合注意力／GDN 缓存的块边界为 **1536 token**，并有 MTP 安全检查点约束，不能假定任意短公共前缀都可复用。

当前 `reader_minutes_schema()` 将可引用事实 ID 放进枚举。Qwen 服务又把整个 Schema 投影到 system message，位置在原文之前。事实从 18 条增长到 19 条时，system 正文只共享 **634 token**，在第一个缓存块之前就发生变化。因此，即便原文的大部分没变，当前纪要请求也无法复用后面的长原文前缀。

抽取批次之间的 system 正文公共前缀约 **1546 token**，仅略超过一块；是否能够命中仍取决于检查点是否建立、保留及缓存压力，不能据此宣称有稳定命中。该分析只计 system 正文，不含 chat template 包装；它是定位输入变化位置的证据，不等于运行时命中率。

```bash
poetry run python scripts/benchmark_prefix_cache.py \
  --analyze-schema --output docs/prefix-schema-analysis.json
```

布局实验将相同的 8K 合成证据与每轮变化的版本字段重排：

| 布局 | 后续两次更新的命中 token | TTFT 中位数 | 总耗时中位数 |
| --- | --- | --- | --- |
| 版本／问题在证据前 | 0 | 3.047 秒 | 4.117 秒 |
| 稳定证据在前，版本／问题在后 | 6144 | 1.002 秒 | 2.009 秒 |

共三组独立会话，每组两次更新，表中排除首次未命中的初始化请求。它验证了稳定前缀布局的收益，但不是已经改造后的 MeetNote 命中率：只调整业务 JSON 键顺序，仍无法绕过前面变化的 Schema。

## 下一阶段的最小上下文层

继续使用内存状态和现有模型，先实现单会议的议题依赖，不引入 PostgreSQL、向量数据库或新的小模型服务。

```text
新增确认发言 → 原文 Source → 局部事实提取 → 证据核验与事实修订
                                              ↓
                         稳定 topic_id + revision + 引用事实集合
                                              ↓
                   只重算受影响议题 → 全局覆盖检查 → 最终成文与审校
```

1. **稳定议题身份**：显示名称可变，`topic_id` 不因改名而重建。新增事实、撤销、负责人或期限修订只递增相关议题版本；跨议题关系使相关两边都失效。
2. **局部结果复用**：缓存键至少包含议题版本、事实及来源集合、任务 Prompt／Schema、模型、tokenizer 和生成设置。旧版本异步任务完成后先校验版本，过期结果不能覆盖新状态。不能只用摘要文本相似度作为缓存键。
3. **覆盖驱动组织**：全局目录列出全部实质议题及现行决定、行动、约束和未决状态，标记各项是否被正文覆盖。检索只补充原文证据，不能决定哪些议题可以消失。审校发现遗漏后重算对应议题；无关议题不再反复生成。
4. **稳定证据前缀**：按来源顺序追加不可变证据块，将变动的版本、问题、差量和映射放在尾部。需共同验证 Qwen 服务的 Schema 投影位置，或采用稳定 Schema 加严格引用验证；不能为缓存收益削弱现有引用、覆盖和修订检查。
5. **责任人与时间**：保留原文时间和可确认的身份来源。未经确认的声纹／Diarization 标签只作说话轮次提示，不能据此自动指定执行人；第一人称承诺的归属必须有可信身份边界。

这不是直接拼接多个小纪要。事实账本先完成全局修订，议题缓存是带事实引用和版本的派生成果，最终文档以当前有效状态为准。会话删除、过期或服务退出后仍释放全部内容；跨会议、跨重启记忆不属于当前实现。

验收应先比较重要议题、现行决定、行动项及负责人／期限的覆盖率和准确性，再比较 token、TTFT、总耗时及资源。分别记录业务结果缓存命中、向量缓存命中和 KV token 命中，不能混成一个“缓存命中率”。参考标注只在模型处理完成后用于评价，不能作为模型输入。至少覆盖后半场切换议题、前后方案修订、否定、提议未批准和身份未确认等情形。

## 本分支已经落地的观测

`stats.by_task` 新增 `cached_tokens`、`cache_reported_requests`、`cache_reported_input_tokens` 和 `cache_hit_ratio`。分母仅统计服务实际报告过缓存计数的请求；上游没有报告时比率为 `null`，不将未知当作未命中。结合已有首输出时间、输入／输出 token 和任务耗时，可以分别定位抽取、成文、审校的成本。

基准与观测已实现；议题缓存、稳定 Schema／投影调整仍是后续需经质量回归的方案。本分支没有改动另一个工作区中已有的 Qwen 引擎改动。
